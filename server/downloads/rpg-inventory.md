# RPG 物品欄原型製作指南

作者：Unity 套件編輯部。這是一份原創開發規格，可直接交給 AI 程式助手分階段實作，也可以由你手動製作。

**目標：** 做出「森林補給站」：玩家收集材料、整理背包、換裝、製作藥水，最後把補給交給守衛。單次流程約 5 分鐘，以完整跑通為目標。

本文件免費下載，可用於個人或商業專案的規劃與實作。文件不附 Unity 套件、第三方程式、美術或商業遊戲素材；使用套件需自行取得相應授權。這是待實作、待驗收的製作指南，並非已測試完成的 Unity 專案。

## 1. 先看哪些示範

- [Opsive 官方試玩](https://opsive.com/demos/ultimate-inventory-system-demo/)：觀察裝備、商店與合成。
- [Opsive Demo Scene 文件](https://opsive.com/support/documentation/ultimate-inventory-system/getting-started/demo-scene/)：對照道具資料與場景元件。
- [Inventory Engine PixelRogue 示範說明](https://inventory-engine-docs.moremountains.com/contents.html)：對照背包、場景切換及武器快捷列。

上述為官方示範。此原型使用自己的情境、數值與素材，並不重製示範內容。

## 2. 選一條實作路線

| 路線 | 物品欄方案                | 本原型的分工                                                    |
| ---- | ------------------------- | --------------------------------------------------------------- |
| A    | Ultimate Inventory System | 使用其物品資料、背包與 UI；依已安裝版本文件設定商店、合成和存檔 |
| B    | Inventory Engine          | 使用其物品、背包與顯示；商店、交易和合成規則由自己的服務實作    |

只選一套作為物品真實資料來源。不要同時維護兩份背包，再用 UI 數字互相同步。沒有套件時，可以先用自己的記憶體資料模型驗證流程，但要明確標記為替身實作。

開始前記錄 Unity 編輯器版本、渲染管線、輸入系統與套件實際版本。先在乾淨場景跑通官方範例，不以本文件推斷相容性。複製需要修改的設定到自己的資料夾，避免更新套件時覆蓋。

## 3. 最小範圍

- 一張小地圖、一名玩家、一個商人、一個合成台、一名守衛。
- 背包 12 格，裝備槽只有武器和護符，快捷列 3 格。
- 支援拾取、使用、移動、堆疊、拆分和丟棄。
- 第一版做單人滑鼠鍵盤操作。多人、重量、耐久與隨機詞綴留到後續。

| 道具 ID | 名稱     | 最大堆疊 | 買入／賣出 | 用途                  |
| ------- | -------- | -------- | ---------- | --------------------- |
| herb    | 月葉草   | 20       | 4／1       | 合成材料              |
| vial    | 空瓶     | 10       | 3／1       | 合成材料              |
| potion  | 回復藥水 | 10       | 15／5      | 回復 20 生命          |
| sword   | 練習劍   | 1        | 30／10     | 武器槽，攻擊加 3      |
| charm   | 木製護符 | 1        | 20／6      | 護符槽，最大生命加 10 |

數值為本原型的設計值。初始生命 50、金幣 25；配方為月葉草 2 + 空瓶 1 → 回復藥水 1。

## 4. 資料與責任

以下為自訂介面的概念名稱，**不是任何套件現成 API**：

- `ItemDefinition`：穩定 ID、顯示名稱、圖示、堆疊上限、可用裝備槽。
- `ItemStack`：道具 ID、數量、必要時的實例 ID。存檔不依賴顯示名稱。
- `InventoryService`：驗證容量與數量，完成交易後發出一次變更事件。
- `EquipmentService`：驗證槽位與裝備條件，再更新屬性。
- `ShopService` / `CraftService`：先驗證所有條件，再一次提交貨幣和道具變動。
- `InventoryView`：顯示資料、送出操作請求，不直接修改金幣或道具數量。
- `SaveAdapter`：把自己的穩定 ID 映射到所選套件的存讀檔方案。

把具體套件呼叫集中在 adapter。實作時必須查閱已安裝版本文件或原始碼，不讓 AI 猜類別與方法名稱。

## 5. 分階段製作

### 階段一：可拾取、可使用

建立 3 種測試物品、背包資料與基本格子 UI。拾取成功才移除世界物件；背包已滿且沒有可合併堆疊時，保留世界物件並顯示原因。滿血時使用藥水不扣數量。

### 階段二：拖放與裝備

每次操作傳遞來源容器、來源槽、目標容器、目標槽及數量。拖放到無效位置時恢復原狀；同類堆疊先合併到上限；不同物品交換前驗證兩邊限制。換裝時確保舊裝備有位置可放，失敗不能讓道具消失。

### 階段三：交易與合成

金幣不足、材料不足或結果放不進背包時，整筆操作失敗。成功後才扣除材料／金幣並發放成果。擋住連點造成的重複提交。不要以「先扣再補回」作為正常交易流程。

### 階段四：存檔與任務完成

保存 schema 版本、場景 ID、物品、裝備、金幣與任務旗標。先寫暫存檔，再以平台可用方式取代主檔並保留備份。守衛需要 3 瓶藥水；提交成功只扣一次，並記錄完成旗標。

## 6. 可貼給 AI 的起始提示

```text
請依「森林補給站」規格建立 Unity 單人物品欄原型。
先讀取專案版本、輸入設定與已安裝套件，列出可確認的 API；未知 API 不要臆造。
先只做階段一：道具資料、拾取、堆疊、使用與 12 格 UI。
保留第三方套件原始碼，把整合放入自有 adapter。
每次交付說明新增檔案、場景設定步驟與實際執行的驗收；未執行的檢查請標示。
在我確認階段一之前，不新增多人、雲端存檔或付費功能。
```

完成一階段後，使用：「沿用現有資料模型完成階段二；先列出會改動的責任邊界，保留既有拾取與使用行為。」逐步推進。

## 7. 驗收清單

- [ ] 同類物品到達上限後建立新堆疊；背包不足時數量總和不變。
- [ ] 無效拖放、裝備類型錯誤、交換失敗時，所有道具數量保持不變。
- [ ] 金幣不足、材料不足或背包已滿時，交易／合成都不扣資源。
- [ ] 快速連點只按實際成功的次數扣除材料，數量不會變成負數。
- [ ] 存檔後重開場景，背包、金幣、裝備與任務旗標一致。
- [ ] 缺失或損壞存檔可提示並安全開始新局，不自動覆蓋可用備份。
- [ ] 開啟背包時不誤觸角色攻擊；關閉後角色操作恢復。
- [ ] 用暫用美術也能從拾取走到守衛交付，完整完成一次流程。
